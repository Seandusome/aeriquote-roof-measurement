# Standalone policy evaluator — implementation contract

Implemented only as pure calculations in `standalone_policy.py`. NOT imported by app.py or any app/server/worker. No app routes, authorization enforcement, database schema, balances, payment connections, stored estimates/images, public policy pages or deletion jobs changed. No current account receives these calculations. Run `python3 -m unittest discover -s tests -p test_standalone_policy.py -v` from repository root. Standard Python library only.

## Settled rules implemented as calculations

- UTC-aware timestamps,120 elapsed24-hour days after explicit paid-access end. Start inclusive/end exclusive. Exact UTC timestamp emitted with microseconds. Original monthly anchor day clamps February and returns to original day in later months, preserving the UTC time-of-day. No real account clock is migrated.
- Cancel stops the NEXT renewal; paid-through access calculated through supplied end. Downgrade is scheduled for next confirmed successful renewal. Schedule says due_unconfirmed if a supplied period has ended; it does not pretend a payment/reset happened. Reset is never applied to any input counters. Monetary proration is not calculated.
- Confirmed current paid periods can be active; pending/failed new periods never mint calculated entitlements. Upgrade pending/failed leaves the supplied existing confirmed plan unchanged. Successful upgrade adds only plan-cap difference; used counts/extras/renewal instant unchanged. Separate lookups/estimates channels.
- Upgrade full reversal removes ONLY attributable unused units in each channel: delta minus consumed. Used upgrade units stay represented in the calculated cap; current plan falls back to the still-confirmed base plan. Example Basic23 +10 upgrade uses, then reversing Pro delta50: remove40, cap35, used33, monthly remaining2; unrelated extras untouched. Fully consumed upgrade removes0; unused upgrade removes50. Never negative remaining or extras. No accounting transaction occurs.
- Successful resubscription can restore still-present content within120days OR a longer documented promise, including after day120. Full versus lightweight protection/presence separate; no claim a lightweight record recreates an image/PDF. Deleted records never promised recovered. Merely evaluating/login never changes usage/extras/deadlines.
- Unknown legacy deadline stays unknown and flagged, not replaced by a guessed120-day deadline. Known shorter promises cannot shorten the120-day base. Longer full protection also protects lightweight fields.

## Explicit snapshot schema

`evaluate(snapshot)` returns a new JSON-compatible advisory result. Inputs must be trusted prevalidated business facts; this function is NOT business/user authentication, payment verification or a ledger audit. It cannot prove a supplied payment really succeeded or that supplied units match database history.

Required:
- `schema:1`, nonempty `business_id`, timezone-aware ISO `now`, boolean `security_eligible`. Security flag must come from existing independent account/employee/business authorization, never client input in an eventual integration.
- `period`: `id`, `start`, `end`, `renewal_anchor`, `plan` (basic/pro/business), `payment_status` (succeeded/pending/failed). Base plan is the confirmed plan before listed upgrades. Period start/end must match original monthly anchor. Current supplied period is explicit, not inferred from account creation or last login.
- `used` and `extras`: each has nonnegative integer `lookups` and `estimates`; booleans rejected. Used is monthly consumption, not extra-bank consumption. Snapshot describes the counters AS THEY EXIST; evaluator never resets them even for a later period.
- `retention`: `paid_access_end`, `legacy_full`, `legacy_lightweight`, `full_present`, `lightweight_present`. Each legacy promise is `{status:none}`, `{status:known,deadline:<aware timestamp>}` or `{status:unknown}`. `none` must mean confirmed absence of a longer promise, not a missing record. Full-present requires lightweight-present. Presence is supplied actual active-storage availability, not inferred from a screenshot/backup. On resubscription retention refers to the prior paid-access end, not the new period end.
- `upgrades`: explicit complete list for supplied period (empty list allowed). Each requires unique `id`, matching `business_id` and `period_id`, `from_plan`,`to_plan`,`payment_status`. Successful records additionally require `confirmed_at`, nonempty `attribution_source`, consumed counts per channel and `reversals` list. Confirmation must be within supplied period and not in the future. Consumed totals cannot exceed recorded usage or delta; base consumption cannot exceed base cap. The attribution source identifies the caller's unit ledger; evaluator does not fetch it.
- Reversal records nested in their upgrade: `id`,`status`; successful records also `kind:full`,`confirmed_at`. Same ID+same entire facts canonicalizes once; same ID with conflicting facts is review-required. Event status history must be canonicalized upstream: do NOT pass pending and successful versions of the same ID as separate facts. This is snapshot deduplication, NOT persisted webhook idempotency.

Optional:
- `cancellation:{requested_at}` means an accepted cancellation for supplied subscription period. Future request rejected.
- `downgrade:<plan>` must lower effective plan. A scheduled next plan is not a newly granted allowance.
- `reactivation:{payment_status,confirmed_at,period_id}`. Successful confirmation must be no later than now, no earlier than prior paid-access end, and match a currently paid active period. Reactivation eligibility at confirmation uses still-present scopes and their protected deadlines. `reactivation_candidate_scopes` independently reports eligibility if resubscribing now; it does not activate anything. Pending/failed reactivation never restores expired content. A separately confirmed current paid subscription may allow NEW work while prior expired content remains unavailable.
- Additional customer/geometry/image-reference fields are ignored and unmodified. Fictional tests include these sentinels and serialize the entire snapshot before/after each evaluation.

Outputs include advisory `access`, `schedule`, `entitlements`, `review_required`, `issues`. Missing/invalid/contradictory required facts return null for the affected calculation and explicit issues. Unknown legacy scope remains null. If any required calculation needs review, actionable-looking permission booleans/readable scopes are suppressed; partial results are diagnostic only. Security denial remains denial regardless of paid status. Never wire these outputs directly into enforcement without a separate authorization/transaction design and verification.

## Deliberate unsupported inputs — information missing, never guessed

Partial financial reversals without attributable unit allocation, reversals crossing period boundaries, reversed chains of multiple upgrades, multiple distinct full reversals, conflicting duplicate facts, unknown legacy clocks and impossible attribution are review-required. Approved reversal principles are settled; these flags mean the provided facts cannot establish which units/periods are affected. No fresh approval of settled rules is needed. A later reconciliation adapter needs explicit allocations, paid-through impact and complete period/event provenance. No reversal of saved work or unrelated extras is permitted.
