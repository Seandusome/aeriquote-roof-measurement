## Receiver boundary

`create_receiver(journal, endpoint_account, invoice_routes, signing_secret, enabled=False)` refuses to start unless explicitly enabled for this local fictional receiver. Requires locally generated `whsec_fixture_` secret, `acct_fixture` endpoint account and server-supplied fictional invoice-to-business routes. Secret generated using `secrets.token_hex` in memory; never written to source/config/evidence or logged. No real endpoint credential was used. This module cannot accept real Stripe test events as-is because its fictional-prefix and local-loopback interlocks are intentional.

Path POST `/qa/stripe-fixture`, JSON, max65536 bytes, loopback remote address only. Reads exact raw request bytes, passes them and Stripe-Signature directly to **official `stripe.Webhook.construct_event(..., tolerance=300)`**. Does not use the SDK bypass-verification helper or reserialize before checking. SDK signature verification is real local HMAC verification against the fictional secret; it is NOT authentication of Stripe origin or real payment. Tests sign independently using HMAC-SHA256 over timestamp + dot + raw bytes. SDK17.1 rejects stale timestamps; receiver also rejects future times beyond300 seconds and ambiguous repeated timestamp fields. Multiple v1 signatures remain SDK-supported but rotation is not separately tested this round.

After signature verification, strict JSON decoding rejects duplicate keys. Pinned snapshot version, object shape, false livemode, allowed invoice notification types, fictional IDs and expected account context required. Optional signed Event.account and optional Stripe-Account header must match the preconfigured endpoint context. Header alone never establishes account identity. Own-account events may omit Event.account; endpoint context and server-owned binding provide the local scope. Unknown invoice routes/wrong binding account rejected. Customer/business metadata is never used to select a business. Local fixed routes are simulated reconciliation context, not canonical Stripe ownership proof.

Only then `LocalJournal.receive` writes the unchanged raw bytes to the existing durable inbox. HTTP200 is receipt acceptance only and occurs after that method returns AFTER transaction COMMIT. Same immutable event duplicates safely; conflicting signed bodies are durably retained/held by existing journal rules. No `supply_simulated_facts`, reconciliation, application or entitlement change is called by the receiver. A valid signed invoice.paid with apparently successful notification fields establishes no payment benefit.

Failures return generic codes: malformed/signature/version/live-mode/type400; account/binding/unmapped/nonlocal403; size413; content-type415; DB/storage failure503. No success response on storage failure. Lost response after a real commit yields503 and later delivery deduplicates. Unsupported/unmapped events are rejected before storage in this narrow fixture receiver; there is no new quarantined unmapped-account inbox yet. Real integration must design that staging/mapping flow rather than guess or silently acknowledge unstored work.
